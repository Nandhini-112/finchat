# Task: Implement Post-Retrieval Filtering in Finora Chat Endpoint

Implement a post-retrieval filtering mechanism in the existing `/api/chat` pipeline to ensure that only facts relevant to the user's question are passed to conflict resolution, calculations and answer generation.

## 1. Implementation Approach

Follow this sequence:

1. Execute the existing SQL retrieval logic without modification.
2. Receive the retrieved financial facts.
3. Apply a new filtering function to the retrieved results.
4. Retain only facts matching the detected query constraints.
5. Pass the filtered facts to the existing downstream processing components.

Do not modify the SQL queries, database schema or fact extraction logic.

## 2. Use Existing Query Metadata

Use the metadata already generated by the intent-classification stage:

- `metricsDetected`
- `entitiesDetected`
- `periodsDetected`

Do not create another intent classifier or independently reclassify the user's question.

## 3. Metric Filtering

Implement metric matching using normalized canonical metric names and explicitly supported synonyms.

Example:

User asks: `What is the net profit?`

Retain:
- Net profit
- Net profit for the period
- Net income (only if mapped to the same canonical metric)

Exclude:
- Gross profit
- Operating profit
- Profit before tax

Do not use broad substring matching such as `includes('profit')`.

Support multiple requested metrics when the user explicitly asks for a comparison.

## 4. Entity Filtering

Ensure retrieved facts belong to the requested entity.

Example:

Requested entity: `Contoso Logistics LLC`

Retain facts belonging to Contoso Logistics LLC.

Exclude:
- Contoso Retail
- Contoso Properties
- Unrelated entities
- Generic dimension labels such as Category Breakdown

Use normalized entity matching while avoiding accidental partial matches.

## 5. Reporting Period Filtering

Ensure retrieved facts match the requested reporting period.

Example:

Requested period: `Q1 2026`

Retain Q1 2026 facts.

Exclude:
- Q2 2026
- FY2026
- Other reporting periods
- Facts with unspecified periods when the user explicitly requests Q1 2026.

Do not treat different reporting periods as equivalent.

## 6. Missing or Ambiguous Metadata

- Do not automatically include facts when required metadata is missing.
- Do not guess an entity, metric or reporting period.
- If a fact cannot be reliably matched, exclude it from the filtered result and record a diagnostic reason.
- If filtering removes all relevant facts, return the existing insufficient-evidence response rather than generating an unsupported answer.

## 7. Integration Requirements

Integrate the filtering function immediately after the existing SQL fact retrieval and before:

- Conflict resolution
- Calculation engine
- AI conflict analysis
- Answer generation

Ensure all downstream components receive the filtered facts instead of the original unfiltered results.

Preserve the existing conflict-resolution algorithm and source authority ranking.

Do not modify:
- SQL retrieval queries
- Financial fact extraction
- Document ingestion
- Database schema
- Azure AI Search indexing
- Authentication
- Existing API response structure

## 8. Logging and Validation

Add diagnostic logging for:

- Total facts retrieved.
- Number of facts retained.
- Number of facts excluded.
- Exclusion reasons (metric mismatch, entity mismatch, period mismatch or missing metadata).

Do not log sensitive document contents or unnecessary personal information.

## 9. Testing

Test the following query:

`What is the net profit of Contoso Logistics LLC for Q1 2026?`

Verify that:

- Only Net Profit facts are retained.
- Gross Profit is excluded.
- Operating Profit is excluded.
- Profit Before Tax is excluded.
- Contoso Retail records are excluded.
- Q2 2026 records are excluded.
- FY2026 budget records are excluded.
- Unspecified-period records are excluded.

Also test queries requesting multiple metrics to ensure all explicitly requested metrics are retained.

## 10. Final Deliverables

Provide:

1. New filtering function and its location.
2. Existing chat handler integration changes.
3. Before-and-after retrieval counts.
4. Test results for all scenarios.
5. Confirmation that SQL queries, extraction, ingestion and conflict-resolution implementation remain unchanged.

**Important:** Inspect the existing code and actual data structures before implementation. Reuse existing metadata and field names. Make the smallest possible code change. Do not rewrite existing modules or deploy the application.
